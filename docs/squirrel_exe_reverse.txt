SquirrelReceiver.exe — full reverse (Goggles 3 IP liveview)
==========================================================

File is a Windows Store / Rust GUI. It talks UDP :9003 to DJI Goggles 3
when they "Share Live View". We did not commit the .exe.

This is the protocol as recovered from rdata + Wireshark on a real G3.
If the binary and the goggles disagree, trust the goggles.

Checked on Goggles 3 only. Not G2, not Integra.

2. What this program actually is
--------------------------------

A Store overlay around an open UDP stream.

There is no session key. There is no HMAC. Byte 7 of the header is XOR
of the first seven bytes. The 48-byte handshake is a literal in rdata;
only the session u16 is patched.

Then they built:

    - activation_overlay.rs   DEMO / ACTIVATED / REVOKED
    - entitlement\store.rs    LUT, record, 4:3, RTSP gated
    - bitrate "boost"         23-byte DUML on MI04, not encrypted
    - Windows-only RNDIS      Mac has to fake Ethernet in userspace
                              to speak the same 8-byte header

The paywall is in the compositor. The socket does not care.


3. Network
----------

    Join                         Goggles                  You
    ---------------------------  -----------------------  ----------------------
    Wi-Fi "share to phone"       192.168.2.1:9003         DHCP on goggles SSID
    USB Remote NDIS (Win)        192.168.60.2:9003        192.168.60.1/24, no gw
    USB on macOS                 same                     tetherkit-cli -> feth0

UDP only. Local port on the PC is typically ephemeral; they send to 9003
on the goggles. Bind 0.0.0.0 or 192.168.60.1 for wired.

OTG on the goggles is the PHONE/gadget path (our method 1). For this
UDP path OTG stays off so G3 remains a USB device (RNDIS).


4. UDP header (every packet, 8 bytes, little-endian)
----------------------------------------------------

    offset  type   field
    0       u16    length | 0x8000     bit15 always set
    2       u16    session
    4       u16    seq
    6       u8     type
    7       u8     xor(bytes[0..7))    i.e. xor of the first 7 bytes

Reject if byte7 is wrong. Reject if (length & 0x7FFF) != packet size.

    type  name
    0     handshake
    1     data / windows / DUML
    2     video
    3     file
    4     ACK (client -> goggles)
    5     command
    6     extra ACK

Type-2 seq steps by 8 (low 3 bits stay 0). Handshake seed for type-2
sits at offset 8 of the type-0 packet (u16).


5. Type 0 — handshake (48 bytes)
--------------------------------

Template from rdata @ 0x141543120 (hex):

    30 80 3A DD 00 00 00 57
    D0 E9 64 00 64 00 C0 05
    14 00 00 0A 00
    64 00 64 00 C0 05 14 00
    00 64 00 14 00
    64 00 C0 05 14 00 00 64
    00 01 01 04 0A 02

    30 80          length 0x0030 | 0x8000
    3A DD          session 0xDD3A in the template
    00 00          seq
    00             type 0
    57             xor of the previous 7
    D0 E9          seed 0xE9D0  (this is what type-2 seq starts from
                   if you use this template session; we patch session
                   and recompute xor)

Build:

    copy template
    write session at [2:4]
    rewrite length flag at [0:2]
    byte[7] = xor(byte[0] .. byte[6])

Client retransmits type-0 until type-1/2 show up. No crypto.


6. Type 2 — video
-----------------

    offset  field
    0..7    header
    8       u16 window_start
    10      u16 window_end
    0x10    u8  frame index
    0x11    bits: n_parts in low 7, part index packed with 0x12
    0x14    H.264 Annex-B  (VIDEO_HEADER = 0x14)

part = (b[0x11] >> 7) | ((b[0x12] & 0x1F) << 1)
n_parts = b[0x11] & 0x7F

Reassemble parts 0 .. n_parts-1 of the same frame index, concat H.264.
G3 liveview is High Profile, long P-slice runs, almost no IDR.
Hardware decoders that wait for a RAP hang. Their Windows build
"just works" because something in that process already shows all
slices (libav FLAG2_SHOW_ALL or equivalent). They never wrote that
down, so everyone else debugs USB for a week.


7. Type 4 — ACK (required)
--------------------------

If you stop sending type-4, the source dies. Overlay can still say
ACTIVATED. There is no second keepalive.

    offset          field
    0..7            header, type=4, seq usually 0
    8               u16  type2 window_start
    10              u16  type2 window_end
    12              u16  resend_count
    14              u16  resend[0]
    14+2*n          ...
    then            u16 type3_start, type3_end, u16 zero
    then            u16 type5_start, type5_end, u16 zero, u16 zero,
                    u16 duml_len
    then            optional DUML bytes

Resend list = missing type-2 sequence numbers, in gap order, step 8.
THE LIST IS IGNORED UNLESS IT STARTS AT THE FIRST HOLE.

That is in rtx.rs. Their own UI advertises "Loss recovery". If the
list is shuffled or starts at a later gap, G3 throws the whole ACK
away and you get "random" Wi-Fi artefacting. The goggles are being
literal. The client is being sloppy.


8. Type 1 — data
----------------

~10 Hz after handshake.

    [8]  u16 window_start
    [10] u16 window_end
    [0x10] type3 window
    [0x18] type5 window
    [32] u16 duml_len
    [34] DUML blob (0x55 ...)

DUML v1: 0x55, len in low 10 bits of u16 at [1], CRC8 of first 3
bytes at [3] seed 0x77, CRC16 of body seed 0x3692. Same tables as
every other DJI MB dump on the internet.

    sender 0x1B = goggles
    sender 0x02 = app
    cmdset 0x00 general, 0x02 camera, 0x51 appears on MI04 boost, ...


9. Type 5
---------

Command wrapper. Seq step 8 like type-2. Body starts with two windows,
then counter, 0x01 0x00 0x00, then DUML.


10. MI04 bitrate hint (optional, USB, not UDP)
----------------------------------------------

Composite device 2CA3:0020

    if 0,1    RNDIS          Windows in-box / tetherkit on Mac
    if 4      vendor ff/43/01  bulk OUT+IN     "MI04"

TetherKit claims 0+1. Leave 4 alone: claim_interface, do NOT
set_configuration, do NOT reset, or RNDIS dies. If their boost
worker resets the composite device, that is a bug they shipped.

DUML on MI04 (bitrate.rs):

    sender     0x1B
    receiver   0xEE
    cmdset     0x51
    cmd        0x29
    payload    eb fe ef be 03 00 0f 00 02 01 01 00 00 00 00 01 00 00 00
               + u32le kbps   (default 22500 = 0x57E4)
    period     250 ms (0xFA)

UI minimum they used: 22000 (0x55F0). This is a bitrate *report*,
not a license. Anyone can send it.


11. CRC tables (DUML)
---------------------

CRC8 seed 0x77, CRC16 seed 0x3692. Tables are the public DJI ones
(same 256-byte / 512-byte blobs as in protocol.py). Not a secret.


12. Mistakes in the exe, in order of how much time they wasted
--------------------------------------------------------------

1. Handshake is a constant. Overlay talks like it is a licensed
   session. It is XOR-7.

2. RTX that only works if the first missing seq is first in the
   list. Documented in their own rtx.rs, then the UI lies.

3. High Profile without IDR. Decoder assumed "normal live H.264".
   It is not. FLAG2_SHOW_ALL or you get a black window and blame
   the cable.

4. ACK is the session. Stop ACK, stream dies, overlay still green.

5. MI04 + RNDIS on one composite device. Reset/set_config from the
   boost path kills the NIC. Author clearly tested on Windows with
   the in-box RNDIS driver and never claimed if 4 in parallel
   without a bus reset.

6. Edition gates on LUT / record / 4:3 while the wire is the same
   for DEMO and ACTIVATED. Copied the wrong layer if you used this
   binary as a spec for "what the goggles allow".

7. No Mac RNDIS. They shipped a Store app, not a protocol spec, so
   the same 8-byte header needs a userspace Ethernet kludge on
   Darwin.


13. What we did not copy
------------------------

Store tokens, package identity, activation API, the .exe, their
GStreamer RTSP path, LUT packs, UI.

ip-liveview/ on main is a receiver written from the wire + these
constants. It is not a repack of SquirrelReceiver.
